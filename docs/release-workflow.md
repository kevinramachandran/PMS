# Guarded cloud and on-premises releases

The designated release branches remain `fix/pms-dashboard-permissions-license-20261009` (on-premises) and `cloud-minimal-ui` (cloud). Use their worktrees under `PMS/dist`. Do all future development there. The parent checkout and `cloud-configurable/source` are retained recovery references, not additional development locations. Do not delete them: the workflow fingerprints their source files and blocks releases if they change after review.

## Before a release

1. Review and commit the intended application changes and release tooling in each designated branch. Do not use `git add .`: runtime logs, exports, credentials, and uploads are not release inputs. The gate requires clean source/build/deployment/tooling/documentation inputs, including untracked or ignored source files. It does not require committing runtime logs.
2. If historical sources changed, compare and reconcile those changes first. Only then run `node tools/release/release.cjs audit-legacy --review-note "Describe what was reviewed and reconciled"`, synchronize the audit to the other worktree, and commit it. Never refresh fingerprints merely to silence a failure.
3. Run `node tools/release/release.cjs preflight`. This checks branch identity, committed inputs, and historical-source fingerprints. It does not claim that the build or mobile review has passed.
4. From the exact committed versions, visually test the four register pages at 375, 768, and 1440 pixels in both variants. Check headers, tables, forms, buttons, and navigation, including an open form/menu. Store register and open-form screenshots, their SHA-256 hashes, reviewer, date, and both commit IDs in a review JSON. Use `tools/release/visual-review.example.json` as the schema. Keep review evidence in an ignored local folder such as `dist/release-review/`. Never record a pass based only on automated source tests. Changing either commit invalidates the review.

## One release command

From either active worktree, on Windows with Git, Node, Java, and the Gradle wrapper available:

```powershell
node tools/release/release.cjs release --id 20261012.1 --visual dist/release-review/review.json --notes dist/release-review/changes.md --deliver C:/Users/WIND/Downloads
```

Choose a new release ID every time. The default workspace is the shared `PMS/dist` directory. Use `--workspace <directory>` if it moves. Default output is `<workspace>/releases/verified/<id>/`; `--output` can change that parent directory. `--deliver` is optional; without it, canonical ZIPs remain untouched.

The command cleans and builds each variant separately, runs the full Java and frontend tests, checks the compiled normal sync flow for JSON/API use, and compares the JAR's resources/classes to the build. It verifies mobile assets and cloud register integration. It then checks the pinned package templates, produces exactly the standard 15 ZIP entries, verifies hashes, and rechecks both source states. There are no skip-test, force-release, or dirty-source overrides.

Two named tests using optional historical customer CSV fixtures may be skipped, as documented in `allowed-test-skips.json`; unexpected skips block packaging. Mandatory JSON/API tests must execute. Each ZIP's README records release ID, variant, source commit, and JAR checksum without changing the standard archive layout.

Only after both packages pass does delivery replace `PMS-4.zip` and `PMS-4-cloud.zip` in the requested folder. Prior canonical ZIPs are backed up under `previous-releases/<id>`; a copy failure restores both. Release manifests, test/build logs, notes, and visual evidence remain alongside the dated ZIPs, outside the customer package. The normal output already lives inside the parent `dist/releases` tree; the manifest identifies the authoritative dated release. Do not subsequently copy ZIPs from older folders.

## Maintained inputs and limits

`tools/release/release-config.json` records the source directories, branches, input paths, and visual matrix. The baseline `tools/release/package/{onprem,cloud}` files were extracted from the corrected standard packages. Their pinned hashes protect `.env` port/DB support and instance-specific service behavior. Changing a launcher requires reviewing its behavior and deliberately updating the corresponding pins; do not substitute old deployment scripts.

Run `node --test tools/release/release.test.cjs` when changing the workflow. The source fingerprints detect changes in known historical locations; they cannot discover unknown folders or unpublished work on another computer. No Git push, server deployment, or automatic approval of visual evidence is performed. Visual evidence is a human/browser review record, not proof generated by a source-code scan.

The initial recovery remains uncommitted in the current worktrees. The new preflight is expected to block until those changes are reviewed and committed. Do not fabricate clean state or visual evidence to produce a release.
